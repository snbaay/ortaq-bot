# Ortaq 2.0 architecture

## Observed baseline

`HomeTelegramBot` is a single-thread long-polling consumer. It registers command menu entries, registers members on any group text, routes parsed commands through `CommandRouter`, and routes any other digit-leading group text to `ExpenseHandler.handlePlainExpense`. It currently ignores callback queries and non-text messages. Area handlers call Spring services/repositories; services use JPA and `@Transactional` in several places. Existing entities are `Household`, `Member`, `Expense`, `ExpenseShare`, `CookingSchedule`, `CookingSwap`, `ShoppingItem`, `Note`, `ChoreLog`, and `PaymentDeadline`. Balances aggregate expenses and shares; `Expense.settlement` distinguishes repayments. `DigestJob` polls every 15 minutes, sends a morning digest and upcoming deadline text, and records `Household.lastDigestDate` after delivery. Before V2-00-02, `application.yml` used H2 file storage in dev and Neon-compatible PostgreSQL in prod, both with `ddl-auto=update`; the migration section below records the current V2-00-02 configuration. Current tests cover many service paths but do not establish safe callback or prompt behavior. This is a target design, not a claim that these V2 features already exist.

## Message ingress and routing

Keep the existing long-polling starter and Telegram client. Make `HomeTelegramBot` a small dispatcher: command messages to `CommandRouter`, callback queries to `CallbackRouter`, and reply-to-bot-prompt messages to `InteractionReplyRouter`. All other group text, including digit-leading text, is ignored for expenses. Non-text updates are accepted only for an active photo prompt. Always answer callback queries quickly, including stale/denied ones, then edit a user-owned bot message or send a short group result. Use compact callback payloads such as `v2:p:<opaque-token>:<action>` under Telegram's byte limit; lookup server-side state rather than embedding IDs or amounts as authority. Validate callback query message chat ID, Telegram sender ID, original message ID, token version, and target household. `CallbackRouter` delegates to area handlers; do not put business logic in the bot.

Add small `bot.menu`, `bot.callback`, `bot.interaction`, and area handler classes; `service.PurchaseService`, `RepaymentRequestService`, `CookingEventService`, `CallService`, `NotificationService`, `HouseholdSettingsService`; `domain` and `repository` pairs only as the schema requires. Keep `ExpenseSplitter`, `DebtCalculator`, and parsers pure. Keep localized strings in `messages_kk.properties` through `MessageService`. A shared menu message may be clicked by different members: each callback creates/opens that member's own session, and edits only that member's prompt or message. Group announcements use one shared event row with independently stored responses.

## Sessions and authorization

Persist `interaction_session`: `id` UUID/opaque token PK, `household_id` FK, `telegram_user_id`, `chat_id`, `kind`, `state`, `prompt_message_id` nullable, `menu_message_id` nullable, `payload_json` or narrow typed fields, `version`, `created_at`, `expires_at`, `closed_at`. Index `(household_id, telegram_user_id, kind, closed_at)` and `expires_at`. At most one active draft per user, household and kind; opening a new one offers resume/discard, rather than silently replacing it. Ten-minute input prompt TTL and 30-minute basket TTL; expiry cleanup does not affect confirmed records. Any reply must match the prompt message ID, group, user and active state. `ForceReply` helps the client UI but the server-side match is decisive. Persist sessions so restart does not turn stray text into input or lose a committed basket; stale prompts show a restart/expiry message. Telegram update ID/callback ID goes into `processed_update` with unique `(bot_identity, update_id)` or unique callback ID, creation time and bounded retention; persistent domain uniqueness is the final guard if Telegram retries. Command side effects also need update deduplication. Never trust Telegram username as identity; first verify group membership and `AllowedChats`, then query household-scoped rows. User roles: member, manager, and event initiator/owner. Manager assignment and transfer must be explicit, auditable and household scoped.

## Additive schema, relationships and constraints

Retain all old tables and rows, IDs, settlement meaning, and `Household.lastDigestDate`. Add nullable or new-table structures; never rewrite old ledger rows. Proposed PostgreSQL types below have H2-compatible JPA mappings or equivalent test migration scripts. All money uses `NUMERIC(12,2)` and Java `BigDecimal`; all instants are stored as UTC timestamps and displayed in `Asia/Almaty`, while `LocalDate` occurrence keys are Almaty dates.

Do not add a separate balance table. A shared purchase calls the existing split logic once and links to one expense; personal purchases never call it. The receipt total is the sum of items, and for shared purchases equals the linked expense amount. Do not count `Purchase` separately in balance or monthly report. Existing queries still exclude `deleted=true` expenses; voiding a purchase soft-deletes its linked expense atomically. Settlements are represented only by the existing expense/share ledger after a request is recipient-confirmed. A pending request does not alter balance. For `/oshiru` on new confirmed repayments, route to a compensating correction request accepted by both parties rather than deleting unilaterally; historical rows use the existing policy until explicitly audited.

## Transactions, contention and delivery

Use one service transaction for final basket confirmation: lock session/purchase row (`@Version` or pessimistic lock), validate owner, status, participants and amount, create purchase items and at most one expense with shares, write confirmation key, then commit. Unique keys make repeated callbacks return the existing result. Use the same pattern for repayment acceptance, ready events, poll creation and social calls. Handle uniqueness violations by querying the existing row; never simply retry a write without checking. Keep Telegram HTTP calls outside DB transactions. Create a durable notification row in the domain transaction, then send asynchronously through the existing scheduler or a small scheduled dispatcher. Telegram has no transactional send with PostgreSQL; a crash after Telegram accepted a message but before SENT is recorded can duplicate an announcement. Prefer editing/reusing a stored message ID when possible, keep retries bounded, and document this residual delivery limit. Do not claim exactly-once Telegram delivery. Once-per-event durable keys prevent routine duplicate scheduling across restarts. For the old morning digest, migrate carefully: preserve `last_digest_date`, seed delivery state from it, and avoid sending an extra digest on cutover.

## Migration, deployment and rollback

Before V2-00-02, `ddl-auto=update` ran in production. The V2-00-02 code introduces Flyway version 1: clean installations create the ten legacy tables, while complete existing schemas are checked then baselined without recreating rows. Dev uses Flyway followed by Hibernate `validate`. The repository production profile now uses Hibernate `validate` and keeps Flyway disabled; this has not been deployed. The owner-reported PostgreSQL 18 staging rehearsal validated the legacy schema with Flyway 10.10.0 but emitted a server compatibility warning. Flyway 11.14.1 is pinned pending a repeat staging run against the existing history. Production migration remains a separately approved human cutover. Subsequent scripts create only new tables/indexes and nullable columns. Use a **verified encrypted Neon backup/snapshot** and a restore rehearsal before production. Run preflight queries for row counts, sums of active expense amounts/shares, settlement counts, and per-household balances; compare after migration and after rollout. Never reset the Neon DB or drop old tables. Rollback application first to the last compatible artifact; leave additive tables in place. If a new migration breaks old code, restore into a new database from the snapshot and switch the service only after a human verifies ledger reconciliation. A financial data rollback is a human decision because writes after the snapshot may be lost; export/reconcile them first. See `ORTAQ_V2_RELEASE.md`.

## Operational limits

Use one polling instance per bot token; a separate development bot and database. Telegram bots cannot call users, cannot DM a user who has not started the bot, cannot guarantee delivery, and may receive callbacks on old/forwarded messages. Check current Telegram sticker requirements before assets are produced. Keep long polling, JPA and Spring scheduling; no Redis, Kafka, local Docker, or microservices. Limit retention of deduplication keys, expired sessions and old delivery attempts without deleting ledger/audit rows. Do not log tokens, full message text, receipt file IDs, or banking details. Validate file IDs as opaque strings, restrict photo MIME and size, and never expose them across households.
